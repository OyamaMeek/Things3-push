# Things3 到 GitHub Markdown 同步 MVP 设计

## 背景

本项目需要在 macOS 上只读监听 Things3 数据库，将任务导出为结构化 Markdown，并通过 Git 自动提交和推送到用户已配置的远端仓库。

仓库中的 `Agent.md` 描述了完整产品愿景，但当前主项目尚无实现。内嵌的 `things.py` 1.0.1 参考库公开的是返回稀疏字典的函数接口，而不是 `Task`、`Project`、`Area` 类；它也不提供优先级、Evening 等字段。因此 MVP 以参考库的真实只读数据为准，不输出无法可靠获得的字段。

## 目标

MVP 必须做到：

1. 启动时读取完整 Things3 快照并同步 Markdown。
2. 监听 Things3 SQLite 数据库及其 WAL/SHM 变化，经防抖后再次同步。
3. 使用确定性渲染和原子文件替换，使内容未变化时不写磁盘、不产生 Git diff。
4. 自动暂存同步器实际变更的明确路径，按配置提交并推送。
5. 定时运行同一套完整快照同步，修复遗漏或漂移。
6. 捕获 `SIGINT` 和 `SIGTERM`，停止接收新工作并等待当前同步结束。
7. 提供安装、配置、前台运行与 launchd 部署文档和自动化测试。

## 非目标

MVP 不包括：

- 从 Markdown 写回 Things3。
- Things 附件同步。
- 自动 merge、rebase 或解决 Git 冲突。
- 从底层数据库私有字段推导 `things.py` 未公开的优先级、Evening 或重复规则。
- Web 管理界面和性能监控面板。
- 对真实 GitHub 远端或真实用户 Things 数据库执行自动化集成测试。

## 关键决策

### 同步策略

采用“防抖后的确定性完整快照”策略，而不是在 MVP 中维护独立的增量写入路径。

每次同步均执行：

```text
读取完整只读快照
  -> 规范化数据
  -> 渲染期望文件集合
  -> 原子协调磁盘
  -> 明确暂存变更路径
  -> 可选提交
  -> 可选推送
```

SQLite 文件变化事件无法直接指出发生变化的任务。即使做 UUID 级增量更新，也必须先读取新快照做差异比较。完整快照渲染可同时正确处理任务移动、删除、容器重命名和 Today/Upcoming 派生视图，并让启动同步、监听同步和定时校验复用同一条代码路径。

完整快照不意味着无条件重写文件。文件协调器先比较字节内容，只替换发生变化的文件。由此，单个标题变化通常只产生对应标题行的 Git diff。

### 文件所有权

同步器完全管理它生成的 Markdown 内容，但删除操作采用保守边界：

- 每个生成文件包含稳定的生成标识。
- 仅删除位于已知导出路径中、带生成标识且不再属于期望快照的文件。
- 未带生成标识的陌生文件始终保留并记录警告。
- 同步器不使用笼统的目录递归删除处理未知内容。

该规则兼顾确定性全量协调和用户文件保护。

### 主位置与派生视图

每个任务只有一个主位置，优先级如下：

1. 所属 Project。
2. 所属 Area。
3. `Inbox`、`Anytime` 或 `Someday` 顶层列表。

`Today.md` 和 `Upcoming.md` 是派生视图，允许重复展示已有主位置的任务。Today 的语义直接复用 `things.today()`，不根据单一 `start` 字段自行重建。

## 架构

### `src/config.py`

负责读取和验证 `.env` 配置，向其他模块提供类型化配置对象。配置包括：

- `REPO_PATH`：目标 Git 仓库绝对路径。
- `THINGSDB`：可选数据库覆盖路径；缺省时使用 `things.py` 自带的路径发现。
- `LOG_LEVEL`、`LOG_MAX_BYTES`、`LOG_BACKUP_COUNT`。
- `WATCH_DEBOUNCE_SECONDS`。
- `FULL_SYNC_INTERVAL`。
- `AUTO_COMMIT`、`AUTO_PUSH`。
- `GIT_REMOTE`、`GIT_BRANCH`。
- Git 子进程超时。

约束：`AUTO_PUSH=true` 时必须启用 `AUTO_COMMIT`。目标路径必须存在且为 Git 工作树。敏感配置不写入日志。

### `src/models.py`

定义项目内部不可变数据模型，将外部稀疏字典与渲染逻辑隔离。主要实体为：

- `TaskSnapshot`
- `ChecklistItem`
- `ContainerSnapshot`
- `ThingsSnapshot`

可选字段有明确的 `None` 或空集合默认值。状态只接受 `incomplete`、`completed`、`canceled`；类型只接受 MVP 用到的 `to-do`、`project`、`heading`。

### `src/things_adapter.py`

只使用 `things` 的读取接口：`tasks()`、`areas()`、`today()`、`upcoming()` 等，并把结果规范化为内部模型。

该模块不导入或调用 `complete()`，也不构造 `update`/`update-project` URL。数据库访问失败后等待 10 秒重试，最多 3 次。只有读取并规范化完整快照成功后才向调用方返回结果。

数据库定位遵循：

1. 显式 `THINGSDB`。
2. `things.py` 对现代 `ThingsData-*` 路径的发现。
3. 参考库的旧路径回退。

### `src/renderer.py`

输入一个 `ThingsSnapshot`，输出 `dict[Path, str]`，键是相对于目标仓库的安全路径，值是确定性 UTF-8 Markdown 内容。

职责包括：

- 分配任务主位置和终态文件。
- 构造 Today/Upcoming 派生视图。
- 对任务进行稳定排序。
- 渲染任务区块、UUID 注释、元数据和 checklist。
- 清理文件名并解决路径冲突。
- 转义会破坏 Markdown 结构的单行内容。

该模块不读取或写入文件，也不执行 Git。

### `src/filesystem.py`

协调期望文件集合与目标仓库当前状态：

- 内容相同的文件不写入。
- 新内容先写入目标文件同目录下的临时文件，刷新后使用 `os.replace()` 原子替换。
- 删除不再存在的旧托管文件。
- 保留所有陌生文件。
- 返回新增、修改、删除的明确相对路径集合，供 Git 层使用。

一次同步先完成快照读取和全部内容渲染，再开始修改目标仓库，避免数据库读取失败造成部分输出。

### `src/git_ops.py`

通过 `subprocess.run()` 封装 Git 命令，统一捕获 stdout、stderr 和超时。所有命令都设置工作目录和超时。

行为规则：

- 只执行 `git add -- <明确路径列表>`，不使用 `git add .`。
- 删除路径同样通过明确 pathspec 暂存。
- 仅当暂存区含同步器产生的差异时提交。
- 提交消息格式为：`Update: YYYY-MM-DD HH:MM | Added N, Modified N, Deleted N`。
- `AUTO_PUSH=true` 时执行 `git push <remote> <branch>`。
- 不自动 pull、merge 或 rebase。
- Git 失败时保留已落盘内容及本地提交，记录可操作的错误信息，等待下一次同步重试。
- 不暂存或修改仓库中其他未提交内容。

### `src/sync_engine.py`

协调一次同步，并使用互斥锁保证进程内最多只有一个同步执行：

1. 获取完整 Things 快照。
2. 渲染期望文件。
3. 协调文件系统。
4. 无变化时结束。
5. 按配置提交和推送。
6. 记录耗时、文件数量和结果。

启动同步、监听事件和定时校验均调用此入口。

### `src/watcher.py`

使用 `watchdog` 监听实际数据库文件所在目录，关注：

- `main.sqlite`
- `main.sqlite-wal`
- `main.sqlite-shm`

相关事件在配置的防抖窗口内合并为一次同步请求。事件处理线程不直接执行同步，而把请求交给串行协调逻辑。新事件若发生在同步期间，会在当前同步结束后至多补跑一次，避免丢失最终状态或形成无限并发。

### `main.py`

应用入口负责：

1. 加载配置和初始化轮转日志。
2. 注册 `SIGINT`、`SIGTERM`。
3. 创建同步引擎并执行启动同步。
4. 启动文件监听与定时完整同步。
5. 退出时停止接收新请求，关闭监听和定时器，等待当前 Git 操作在既定超时内结束。

## 输出结构

```text
<REPO_PATH>/
├── Inbox.md
├── Today.md
├── Anytime.md
├── Someday.md
├── Upcoming.md
├── 已完成.md
├── 已取消.md
├── Projects/
│   └── <项目名>/
│       ├── tasks.md
│       ├── 已完成.md
│       └── 已取消.md
├── Areas/
│   └── <领域名>/
│       ├── tasks.md
│       ├── 已完成.md
│       └── 已取消.md
└── Archived/
    ├── Projects/
    └── Areas/
```

空的固定顶层视图仍生成，以保持结构稳定。空 Project/Area 是否保留由当前快照中容器是否存在决定：存在的空容器保留目录和空的托管文件；消失或进入回收站的容器导出目录移入对应 `Archived` 子目录。

由于 `things.py` 的 Area API 不提供可靠的回收站状态，Area 从快照消失只表示导出侧不再可见，不声称它在 Things 中具有特定“归档”状态。

## 路径规则

文件名清理遵循以下规则：

- 将 `/`、`:`、`?`、`*`、`<`、`>`、`|`、`"` 和控制字符替换为 `-`。
- 去除首尾空白和结尾句点。
- 空名称使用实体类型加 UUID 短前缀。
- 限制单个路径段长度，为 `.md` 和冲突后缀预留空间。
- 两个名称清理后相同，或在默认不区分大小写的 macOS 文件系统上发生大小写冲突时，为所有冲突项追加稳定 UUID 短后缀。

路径分配只依赖实体 UUID 和标题，同一快照的结果始终一致。

## Markdown 合同

每个文件第一行使用固定生成标识，随后是标题和任务区块。任务区块示例：

```markdown
## [ ] 任务标题
<!-- uuid: ABC123DEF456 -->
- **创建时间**: 2025-01-15 10:30
- **修改时间**: 2025-01-15 14:20
- **开始日期**: 2025-01-16
- **截止日期**: 2025-01-20
- **提醒时间**: 09:00
- **项目**: 项目 A
- **领域**: 工作
- **标题分组**: 下一步
- **标签**: #工作 #重要
- **备注**:
  任务的详细描述内容
- **子任务**:
  - [ ] 子任务 1 <!-- uuid: SUB123 -->
  - [x] 子任务 2 <!-- uuid: SUB456 -->

---
```

规则：

- `incomplete`、`completed`、`canceled` 分别映射为 `[ ]`、`[x]`、`[-]`。
- 缺失的可选字段整行省略，不输出空占位。
- 不输出参考库没有公开提供的优先级和 Evening 字段。
- 标题和单行字段转义换行及结构性 Markdown 字符。
- Notes 保留多行文本，统一换行符并缩进，使其保持在备注字段下。
- Checklist 项包含 UUID 和状态；可用时保留完成时间。
- UUID 是区块稳定身份，不从标题或路径推导。
- 文件和任务使用稳定排序，避免无业务变化的重新排列。

## 容器移动与归档

文件协调前，渲染器根据当前快照产生当前 Project/Area 路径映射。协调器还读取上一轮生成清单，以 UUID 识别容器重命名、消失和重新出现：

- 重命名：将托管内容写入新路径，删除旧路径下的托管文件；陌生文件留在原目录并告警。
- 消失或进入回收站：将仅含托管文件的导出目录移到 `Archived/Projects` 或 `Archived/Areas`；若含陌生文件，不移动整个目录，只归档托管文件并保留陌生内容。
- 重新出现：从当前快照生成到活动路径；不会自动搬回用户添加的陌生文件。

`Archived/` 是持久历史区，不属于“当前期望文件集合”的删除范围。已归档的托管文件会保留到用户显式清理；若同一容器 UUID 后续再次归档，则更新该 UUID 对应的归档位置，而不是创建无限重复副本。活动路径永远只反映当前快照。

同步器维护一个带生成标识的清单文件，记录活动容器映射、归档容器 UUID、相对路径和托管文件集合。该清单属于同步器管理范围，并参与明确路径 Git 暂存。

## 错误处理

### 数据库读取

- 最多尝试 3 次。
- 每次失败后等待 10 秒，再进行下一次尝试。
- 最终失败时，不进入文件协调和 Git 阶段。
- 记录异常类别和上下文，但不记录 token 或完整敏感路径配置。

### 文件系统

- 单文件写入使用同目录临时文件和原子替换。
- 临时文件失败时清理自身，不删除原文件。
- 某个文件协调失败会终止该轮 Git 操作，并记录已经成功落盘的路径；下一轮通过确定性快照收敛。

### Git

- 所有子进程有超时。
- 非零退出记录 stderr。
- 提交失败时不推送。
- 推送失败时保留本地提交。
- 远端领先或认证错误不触发自动冲突处理。

## 配置与部署

项目提供：

- `.env.example`
- `requirements.txt`
- `setup.py` 交互式配置脚本
- `generate_launchd.py`
- `main.py`
- README 安装和运维说明

依赖基线：

- Python 3.9+
- `things.py>=1.0.1,<2`
- `watchdog>=2.1,<7`
- `python-dotenv>=0.19,<2`

launchd 生成器在项目内生成 plist 预览。用户通过明确的 setup 步骤安装到 `~/Library/LaunchAgents`，普通同步进程不修改系统 launchd 配置。

## 测试策略

### 单元测试

`tests/test_things_adapter.py`：

- 使用内嵌参考库的 SQLite fixture 或等价测试数据库，通过 `THINGSDB` 注入。
- 验证稀疏字典规范化、状态映射、空字段、Project/Area/Heading 关系。
- 验证失败重试次数和间隔，不真实等待 10 秒。
- 验证适配器只调用读取 API。

`tests/test_renderer.py`：

- 顶层、Project、Area 主位置优先级。
- Today/Upcoming 派生重复展示。
- 完成和取消文件。
- Markdown 特殊字符、多行 Notes、Checklist 状态。
- 路径清理、空标题、重名和大小写冲突。
- 稳定排序和确定性输出。

`tests/test_filesystem.py`：

- 无变化不写入。
- 新增、原子修改、删除旧托管文件。
- 保留陌生文件。
- 容器重命名、归档及含陌生文件时的保守行为。
- 中途失败后下一轮收敛。

`tests/test_git_ops.py`：

- 明确 pathspec 暂存，不出现 `git add .`。
- 空差异不提交。
- 提交消息统计。
- 超时、非零退出和 stderr 日志。
- 提交失败禁止推送，推送开关生效。

`tests/test_service.py`：

- 防抖窗口合并事件。
- 同步期间事件触发至多一次补跑。
- 启动同步、定时同步复用同一入口。
- 优雅退出等待当前任务并停止新任务。

### 集成测试

在临时目录创建 Git 仓库，使用测试数据库完成：

1. 快照生成 Markdown。
2. 修改 fixture 或输入快照后仅产生预期 diff。
3. 任务移动后旧位置消失、新位置出现。
4. 删除或隐藏容器后内容进入 `Archived`。
5. 自动提交只包含托管路径。

真实 GitHub push、真实 Things 数据和 launchd 生命周期作为 README 中的人工验收步骤，不进入默认测试套件。

## 验收标准

MVP 完成时满足：

1. 使用测试数据库启动后能生成完整目录结构和合法 Markdown。
2. 重复同步同一快照时，不修改文件且不创建提交。
3. 单个标题变化的 Git diff 仅包含相应任务标题行，除非排序或路径也确实发生变化。
4. 任务主位置遵循 Project → Area → 顶层列表，Today/Upcoming 正确重复展示。
5. 非托管文件不会被删除或暂存。
6. 数据库读取最终失败时，目标 Markdown 保持不变。
7. Git 命令均有超时，且不使用 `git add .`。
8. 自动提交和自动推送均可通过配置关闭。
9. 文件事件在防抖后触发同步，进程退出信号可优雅停止服务。
10. 自动化测试覆盖数据适配、渲染、文件协调、Git 和服务控制的核心边界。

## 文档同步

实现完成后更新 `Agent.md`：

- 标记 MVP 实际完成的阶段任务。
- 将对象模型描述修正为基于字典的读取 API 与内部规范化模型。
- 删除无法由公开 API 支持的 Markdown 字段承诺，或明确其不在 MVP 范围。
- 更新现代 Things3 数据库路径、Python 最低版本和 `things.py` 依赖版本。
- 说明 MVP 使用单一确定性快照路径，而非两套独立的增量与全量写入实现。
